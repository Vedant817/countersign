# Adversarial review — why this loses, and what to do about it

Two critics were spawned on 24 October 2026 with one brief: **argue why this project fails and wins
nothing.** One played a hackathon judge scoring the five Devpost criteria; one played a payments
domain expert. Neither was asked to be fair, and neither was.

Their findings are recorded here in full because **the value is in the objections, not the fixes** —
a list of things we already intended to do is worthless, whereas a list of things we cannot answer is
the actual risk. My own assessment follows each group.

## Group A — the thesis is aimed at the wrong dispute (fatal if unaddressed)

The strongest objection, and the one I think is correct.

**A1. Intent is not the disputed fact in the disputes that cost merchants money.** SNAD ("not as
described") and INR ("item not received") turn on _delivery and item condition_. A signed mandate is
silent about both. The one case where intent genuinely decides — `UNAUTHORISED` — is adjudicated by
the issuer or PayPal, not by the merchant. So "provable intent" addresses the minority of claims and
cannot move the majority.

**A2. The liability router picks an action; it does not assign liability.** Card chargebacks are
decided by the buyer's issuer under network rules; PayPal's in-house claims are decided by PayPal.
`packages/defender/src/router.ts` mapping `UNAUTHORISED → USER_AUTHORISED → CONTEST` is a local
verdict about a decision someone else makes. The four labels are not states any PayPal API returns.

**A3. SCA/MIT.** Buyer-absent stored-credential variable-amount is precisely the case where
authorisation risk stays with the merchant. A signed intent is not an SCA method and shifts no
liability. In the EU/UK/India the merchant's unauthorised-payment exposure is unchanged by anything
in this repository.

**A4. The evidence packet has no slot for its own innovation.** `provide-evidence` takes a fixed
`evidence_type` enum plus capped notes and documents (`packages/paypal/src/types.ts:710-720`). The
signed chain, SD-JWT, decision record and QR-to-verifier ride as an unstructured blob — and for a card
chargeback the decider is the issuer, which never adjudicates a mandate.

**A5. The evidence is generated by the accused party.** The checkout JWT is signed by Countersign's
single `VI_MERCHANT_KID`, shipments are merchant-asserted via `/track`, and merchant-fault rules
require the merchant to file evidence against itself. EC-MER-4 already concedes we cannot detect
faked delivery.

**My read:** A1–A3 are correct and they are the project's real problem. The honest repositioning is
available and narrower: **Countersign does not decide liability, it produces a tamper-evident record
that a decider can use, and it refuses to assert what it cannot prove.** That is defensible. "We route
liability deterministically" is not, and the pitch says the latter.

The fix is mostly _positioning plus one real feature_: state plainly that SNAD/INR are out of scope
because we do not know delivery truth, and make the `UNAUTHORISED` case excellent — because there, a
signed on-device approval genuinely is evidence no merchant currently has.

## Group B — trust and strategy (serious)

**B1. Trust collapses to "trust Countersign".** The agent key is held server-side by vi-service; the
merchant's Gate and the public verifier both call Countersign's own `/v1/verify`. There is no
independent anchor a merchant or PayPal can check, so "verifiable by anyone" is a website vouching for
itself. Partially mitigated by the public verifier accepting keys from JWKS, but not answered.

**B2. PayPal already holds this.** PayPal has the transaction record, Seller Protection and dispute
tooling, and runs its own agentic-commerce programme. A third party adding a parallel verdict layer
onto PayPal's rail is a risk-ops and support burden, not a product. The mandate format is
Mastercard/Google's Verifiable Intent — a competitor's rail.

**B3. No merchant integrates a new verification layer to accept a payment they already accept.** The
Gate is a per-checkout dependency, dispute filing needs API access to the merchant's PayPal account,
and the benefit is an unproven win-rate.

**My read:** B1 is fair and cheap to improve (publish the verification recipe so a sceptic can check a
record without our server — `verify.py` already exists for this). B2 is not answerable by code and
should be _acknowledged_ rather than argued with; the honest line is "this is what we would build
inside PayPal", which is also a stronger pitch to a PayPal judge than pretending to compete with them.

## Group C — real defects worth fixing now

**C1. Griefing is built into the Gate.** Check 12 suspends a mandate after **3 consecutive BLOCKs**.
Any listing or catalogue can knock a user's agent offline by repeatedly presenting one out-of-mandate
cart. **This is a genuine security defect**, not a product objection, and it is fixable.

**C2. The threat model confuses key _export_ with key _use_.** Non-extractability stops exfiltration;
it does not stop script on the wallet origin driving passkey-backed signing. The design then contests
the user it just failed to protect. §13 concedes this but the pitch does not.

**C3. `/status` claimed this instance can "move money on PayPal".** Fixed in `a4341c3`.

## Group D — presentation (fixable, currently zero)

**D1. `/judge` is a list of what the product does not do.** The first deliberate judge experience is
an apology.

**D2. The purchase dead-ends at a quote.** "Lock price" lands on a page whose own banner says no order
was placed. Criterion 2 (a coherent product) is failed at the terminal action.

**D3. The lab is titled "Lab · AT-M5" and prints base64 signatures.** A judge sees a test harness.

**D4. There is no AI in the product.** `packages/agent/src/index.ts` is `export {}`; nothing in
`apps/**` imports `ai` or `@ai-sdk/openai`. The event requires AI. **This is the single largest gap.**

**D5. The repo is private and nothing is deployed.** Deferred by Vedant, both required at submission.

## Confirmed: check 12 is reachable by a third party (C1, verified in source)

Read `packages/gate/src/velocity.ts` end to end. The mechanic:

```ts
const states = await input.deps.recentAttemptStates(mandateId, VELOCITY.MAX_CONSECUTIVE_BLOCKS + 1)
const blocks = consecutiveBlocks(states.value)          // counts BLOCK states, most recent first
const tooManyBlocks = blocks > VELOCITY.MAX_CONSECUTIVE_BLOCKS   // > 3, so the fourth trips
if (trips) → suspendMandate(mandateId, `velocity guard: ${detail}`)
```

So four consecutive BLOCKed **attempts** move the mandate to `SUSPENDED`. Nothing in the run has to
be the agent's fault.

### Why a third party can forge the signal — and why that is weaker than it first reads

An attempt is BLOCKed when the Gate refuses the cart, and the cart is chosen by **the merchant**. Three
carts priced above the mandate cap produce three BLOCKs, and the fourth suspends the buyer's mandate.

**But the merchant cannot create an attempt.** Attempts are created by the buyer's agent, so the
attack needs the agent to try four times against a cart that keeps failing. A shop cannot suspend a
buyer who walks away — only one who keeps coming back. That is materially weaker than "any listing can
knock a user's agent offline", which is how it was reported and how I repeated it.

What survives is still worth fixing, and it is a different problem:

- **A retrying agent is punished for the merchant's pricing.** An agent that retries a blocked cart
  four times is behaving badly and suspension is arguably the control _working_. But the recorded
  reason is `velocity guard: 4 consecutive block(s)`, which reads as _the agent is compromised_ when
  the truth may be _this shop is too expensive_. The buyer is told the wrong thing about their own
  agent, and the resume path ("review the attempts") does not reveal it either.
- **Injection makes retrying likely.** A listing carrying "retry until it works" is a natural route to
  four attempts, and §13's threat model already concedes an agent loop can be steered.

**Corrected severity: major, not fatal** — a real griefing surface for one plausible agent behaviour,
plus a diagnostic that misattributes the cause.

### Why I am not implementing this in the same pass

The narrow fix — count only agent-attributable BLOCKs — needs the failing check's code on the attempt
row. `AttemptState` is a bare state string (`'CREATED' | 'GATED_BLOCK' | …`, `types.ts:376`) and
`recentAttemptStates` returns only states, so the code would have to be threaded through the
`GateDeps` port, the `@countersign/db` repository and every test double. That is a cross-package change
to a **security control**, and `packages/gate`'s 162 tests all have to keep passing.

A smaller fix is available and is the better first move: **record why the streak tripped.** Put the
first failing check code into the suspension reason and the `REVIEW` message, so a buyer suspended
because a shop was too expensive is told that rather than being told their agent looks compromised.
That is a message change, not a control change, and it removes the misattribution without touching the
signal.

**Status: analysis corrected, implementation deliberately not started.**

### The fix, for when it is done properly

The control exists to catch a **runaway agent**, and a runaway agent is characterised by BLOCKs that
are _its own_ fault. So the streak should count only attempts whose BLOCK is attributable to the
agent's behaviour, not to the cart it was handed. Concretely:

1. `AttemptState` gains the failing check's code (it is already persisted on the decision row, so this
   is a read, not a schema change).
2. `consecutiveBlocks` counts only BLOCKs whose first failing check is _agent-attributable_ —
   `GATE_REPLAY`, `GATE_CHAIN_INVALID`, `GATE_VELOCITY`, `MANDATE_*`. A BLOCK from a cart that simply
   exceeded the mandate (`GATE_PRICE_LOCK`, `GATE_LINE_ITEMS`) does **not** accrue: the buyer's agent
   was told "no" and stopped, which is the control _working_, not failing.
3. The negative case stays: a genuinely runaway agent produces replay/chain failures, and still gets
   suspended on the fourth.

Two properties make this the right fix rather than a patch: the input an attacker controls (the cart)
no longer moves the buyer's state, and the signal that remains is one only the agent can produce.

**Why not simply raise the threshold or rate-limit the suspension:** both keep the vulnerability and
add latency. An attacker who can produce three BLOCKs can produce thirty; a rate limit changes how
often the denial happens, not whether it can.

**Status: analysis complete, implementation not started.** It is a change to a security control, so it
wants a failing test first (one hostile merchant, four over-cap carts, assert the mandate is still
`ACTIVE`) and it touches `packages/gate`'s 162 tests.

## What I would do, in order

1. **Wire the model in (D4)** — the Modal endpoint is deployed and `OPENAI_BASE_URL` works. One real
   LLM call site in the product beats any amount of documentation about one.
2. **Fix the griefing defect (C1)** — a suspension triggered by an attacker-controlled input.
3. **Build the merchant surface (D2, D1)** — AG Studio, per `PRIZE-STRATEGY.md`. It converts a
   dead-end into a product and repairs criteria 2 and 3.
4. **Reposition the pitch (A1–A3)** — narrow the claim to what is provable, and say why SNAD/INR are
   out of scope. A judge who spots the overclaim unaided stops believing everything else.
5. **Fix `/judge` (D1)** — stop opening with what is missing.

## The uncomfortable summary

The engineering in this repository is real: 2,688 tests, a deterministic Gate with twelve checks, a
public verifier, honest refusals where a value cannot be determined. None of the five judging criteria
reward that on its own.

What is missing is a **product a judge can use in ninety seconds**, and an **AI component**. Those are
the two things standing between this and any prize — not correctness, and not effort.

## Found in the running app: three files disagree about spelled-out numbers

Driving `POST /api/intent/compile` with real intents produced two different outcomes for the same gap:

| Intent                                                                   | Result                                                                               |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `"buy the cheapest trail runner under eighty dollars, and nothing else"` | **200** — 2 constraints, 1 blocking ambiguity asking the buyer to confirm the amount |
| `"spend at most fifty dollars on a trail runner from Northwind"`         | **400** — `CS_VALIDATION`, `ec: AT-M8.5`, "please enter the amount by hand"          |

Both sentences spell the amount out. Both should behave the same way. They differ because the outcome
depends on **whether the model chose to emit a cap**, not on anything the buyer wrote.

The three files involved describe three different behaviours:

1. **`literal.ts:21-26`** — _"Spelled-out numbers are not read… That gap is covered by the other half
   of §8.8's rule: the compiler must raise a **blocking ambiguity** instead of guessing. A user who
   writes 'twenty dollars' and is asked 'did you mean $20.00?' **gets a question, not a silent
   rounding**."_
2. **`constraints.ts:622-631`** — returns a hard `CS_VALIDATION`. A question is not what the user gets.
3. **`proposal.ts:249-264`** — _"a clamp and not a refusal… Refusing would send a buyer who wrote a
   perfectly clear limit to the manual form because a model misbehaved."_ That is correct about the
   clamp, and it is what the second half of rule 6 then contradicts.

**Fixed so far: the message, not the behaviour.** It said _"the request does not contain an amount to
support it"_, which is false — the request contains "fifty dollars". It now names the actual gap:
this compiler reads digits, so a number written in words is not one it can present back. Two tests
updated, 285 pass.

**Not fixed: the behaviour.** The documented mitigation is an ambiguity; the code returns an error.
Making `validateConstraints` return an ambiguity instead of an `err` is a control-flow change through
`compile`, `ambiguity.ts` and the AT-M8.3/AT-M8.5 suites, and it changes what a _safety_ check does.
That wants its own pass with a failing test first, not a drive-by — the same call made about check 12.

**Why it matters for the demo:** a judge types a sentence, and whether they get a helpful question or
a red error depends on which number word they happen to use and how the model felt that morning. The
compiler is right to refuse a cap it cannot support; it is wrong to make the refusal depend on a
model's choice about whether to mention one.
